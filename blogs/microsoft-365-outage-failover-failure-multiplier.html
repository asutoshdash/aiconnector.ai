Microsoft 365’s November outage: when failover becomes a failure multiplier

What Microsoft’s preliminary root-cause report reveals, and how to test your AI agents before their dependencies recover.

AIConnector editorial · 18 November 2026 · 7 minute read · Evidence checked 17 November 2026

Imagine a customer-success manager asking an AI agent for the contracts that need renewal this week. The agent starts its work, but the email service it depends on is unavailable.

That is the visible failure.

The harder engineering question comes later: what happens when the service starts recovering and thousands of agents resume their work together?

This is where reliability stops being only a question of whether you have retries. It becomes a question of whether your recovery mechanisms can overwhelm the system they are trying to help.

Our earlier Outlook outage guide focused on how an agent should behave when a dependency is unavailable. This follow-up examines Microsoft’s preliminary root-cause account and turns its lessons into a practical recovery test.

1. What Microsoft has reported

Preliminary findings: this is an analysis of the preliminary report, not a final RCA. Microsoft’s findings may change when its final post-incident report is published.

The report describes the impact window as 12 November at 16:20 UTC to 13 November at 16:10 UTC. Exchange Online experienced the principal disruption, while features in other Microsoft 365 services that depended on it were also affected.

Microsoft identifies three interacting conditions:

  • A gateway-specific Windows defect introduced in July caused lock contention under particular load conditions.
  • A Teams failover changed the traffic and load on the gateway that also supported Exchange.
  • An unrelated issue had taken nearly 14% of gateway capacity out of service.

Traffic was redirected to the remaining servers, increasing pressure on them. Partition boundaries did not contain the cascade, and more than 80% of gateway servers became unresponsive at the worst point.

Recovery was difficult because returning servers were overwhelmed again by waiting traffic. Microsoft restored a known-good code path and gradually brought repaired infrastructure back. Its preliminary report also says the test environment had not exposed the issue’s sensitivity to traffic mix and higher-core hardware. Read the publicly hosted copy of Microsoft’s preliminary post-incident report.

The final report was expected on 20 November. Until then, treat the details above as preliminary.

2. Failover is not the same as spare capacity

Think of a railway station with several ticket counters.

When one counter closes, passengers move to another. That works when the remaining counters have enough spare capacity.

But suppose the remaining counters already have long queues. Moving more passengers does not restore service. It creates a larger queue and slows every transaction. Eventually, the remaining counters can be overwhelmed too.

That is the difference between having an alternative and having an alternative that can safely accept the work.

Ask the next question: how much extra traffic can the failover destination absorb, given its current capacity and current workload?

The following sections are AIConnector’s engineering interpretation and proposed design practices. They are not claims about undisclosed Microsoft internals.

3. Why this matters to agentic applications

An enterprise agent rarely depends on only one service. A contract-summary workflow might call a contract registry, an email connector, a document store, a model endpoint, and a notification service.

It is tempting to regard these as five independent dependencies. They may not be.

Two connectors might share an identity provider. Several tools might use the same API gateway. A fallback path might ultimately reach the same downstream system.

A different tool name is not necessarily a different failure boundary.

Before building recovery logic, map the dependencies underneath the tools:

  • Shared infrastructure: Do tools use the same gateway, identity service, or storage system?
  • Worker capacity: Can one stalled connector consume every available worker?
  • Fallback capacity: Does failover send more work to an already stressed destination?
  • Queue freshness: Can old work expire rather than crowd out urgent requests?
  • Fleet-wide visibility: Does the runtime know a dependency is unhealthy across many agent sessions?

The point is that two separate tools can fail together if they depend on the same component.

4. Healthy enough to probe is not ready for full traffic

A successful request is useful evidence. It is not proof that a recovered service can immediately handle its normal workload plus the accumulated backlog.

Treat recovery as a progression, not a switch.

Step 1: Stop the uncontrolled flow

When a dependency is persistently unhealthy, stop launching unrestricted calls. Separate “we accepted the user’s job” from “we started the downstream operation.”

“Your summary is queued because the email source is temporarily unavailable. No email-based conclusions have been generated yet.”

Do not translate a failed search into “no contracts found.”

Step 2: Probe with a small allowance

Allow a limited number of requests to test recovery. Keep other work queued or return a clear, bounded failure.

The probe should represent meaningful work. A lightweight health endpoint might succeed while a large mailbox query still fails.

Step 3: Restore traffic gradually

Increase permitted concurrency in stages while watching completion rate and latency. If errors rise again, reduce the allowance rather than draining the queue aggressively.

For illustration, a system might allow 2, then 5, then 10 concurrent calls. These are not universal production settings. Choose limits based on the dependency’s capacity, its service agreement, and observed behavior.

Step 4: Drain the backlog deliberately

Recovering work competes with new work.

Prioritize by business value, deadline, and freshness. Expire requests that are no longer useful. Revalidate permissions and approvals where necessary before resuming consequential actions.

The goal is not to empty a queue as quickly as possible. It is to complete useful work without triggering another failure.

5. Put isolation in resources, not just diagrams

Drawing a box around “Email Tools” does not isolate it.

Isolation needs concrete limits: a concurrency allowance, bounded queue, connection budget, or separate worker pool. A stalled email dependency should not consume capacity needed for unrelated document retrieval.

Microsoft’s architecture guidance describes the bulkhead pattern: separating resources into pools so a failure in one area does not consume the rest.

For an agent platform, consider isolation at three levels:

  1. Dependency: One unhealthy provider cannot exhaust all outbound capacity.
  2. Tenant: One customer’s backlog cannot monopolize recovery.
  3. Workflow: An optional enrichment step cannot block essential work indefinitely.

There is a trade-off. Reserved capacity can sit unused, and more partitions create operational complexity. Start with the dependencies whose failure would otherwise affect the largest share of your workload.

6. Run a recovery drill

Use a test environment or a controllable mock dependency. Do not generate load against a real provider without authorization.

Scenario: An email connector fails for ten minutes while agents continue receiving requests. The dependency then returns with limited capacity.

Run the drill in four phases:

  1. Normal: Establish baseline throughput and latency.
  2. Unavailable: Inject timeouts or service errors.
  3. Partially recovered: Allow only a small number of calls to succeed.
  4. Recovered: Restore capacity while retaining the backlog.

Then check:

  • Does the queue remain bounded?
  • Are expired jobs removed or explicitly failed?
  • Can unrelated workflows still complete?
  • Do retries stay within a shared budget?
  • Does the recovered service receive a controlled ramp rather than a burst?
  • Can users distinguish completed, partial, queued, and failed work?
  • Are repeated writes deduplicated if an acknowledgment is lost?

Measure in-flight calls, queue age, admitted and rejected requests, completion rate, and retry traffic. A green health check alone will not answer these questions.

7. What a useful RCA should change

A root-cause report is most valuable when it changes a test, a limit, or an operating procedure.

After reading this incident, an agent-platform team should be able to name:

  • The destination and capacity budget for each fallback.
  • The shared infrastructure behind apparently independent tools.
  • The mechanism that limits recovery traffic.
  • The person or automation authorized to pause backlog draining.
  • The test proving that one unhealthy dependency cannot exhaust the whole runtime.

Those are more useful deliverables than adding “improve resilience” to a backlog.

The takeaway

An agent can be correct about which tool to call and still be unreliable about when, how often, and at what scale to call it.

The practical lesson is not “never fail over” or “never retry.” It is to make recovery respect the capacity that actually exists.

Build for the moment after the outage, not only the moment the outage begins.
